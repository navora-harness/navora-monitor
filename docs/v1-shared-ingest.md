# v1：统一取流框架与实施进度

## 目标与版本边界

基线为 main 的 `d33dc45`（0.4.4）。v1 在独立分支开发，不修改 main 的运行方式。
优先顺序：录像可靠性、消除摄像头重复取流、预览响应、降低本机开销。

同一通道的录像和实时预览共用一个摄像头输入。多个浏览器共享预览输出。
这里减少的是摄像头到服务端的重复流量；本地分发、服务端到观看者的必要流量依然存在。
原始录像不为浏览器兼容性降质，预览可单独转 H.264。

## 架构决策

第一阶段继续使用外部 FFmpeg，不将原生库嵌入 Go 主服务。
Go 的统一取流管理器按通道维护输入会话；一个 FFmpeg 接收摄像头流，复制原编码
并封装为连续 MPEG-TS。Go 通过仅监听 127.0.0.1 的随机端口和随机路径向本机消费者分发。
录像 FFmpeg 和预览 FFmpeg 各读本地 URL，不再直接读取摄像头。

```text
摄像头 -- 一个输入 --> 取流 FFmpeg --> Go 有界分发
                                      ├─ 录像 FFmpeg：原码流分段写盘
                                      └─ 预览 FFmpeg：直通或按需转码
                                             └─ 现有 HTTP 分发 --> 多个浏览器
```

媒体进程故障与 Go 服务隔离。录像和预览仍是独立消费者，故障或停止不主动停止另一个分支。
DLL 可以作为后续取流后端，但不是消除重复连接的前置条件。

## 第一阶段已实现

- 环境变量 `NAVORA_MONITOR_SHARED_INGEST=1` 在服务启动时启用；默认仍走原有链路。
- 同一通道并发申请只启动一个输入进程；会话匹配主 URL 和 RTSP transport。
- 输入保留视频和可选音频，原编码复制；预览分支继续沿用现有 H.264 转码逻辑。
- 统一模式使用 `URL`，不连接 `PreviewURL`。旧配置不被改写。
- 引用计数控制生命周期；最后一个消费者退出 3 秒后关闭输入，期间新消费者可复用连接。
- 输入地址或 transport 改变时，等待旧输入退出，再建立新输入。
- 输入进程退出或超过 20 秒没有输出时，关闭本地输出，让消费者发现断流。
- 下次消费者申请创建新输入，后续申请共享这个替代会话。
- 每个消费者最多缓存 128 个输出块，每块最多 32 KiB；慢消费者断开，不阻塞其他消费者。
- 复用已有 512 KiB 启动缓存；HTTP 写入设有 3 秒超时。
- 服务停止时统一关闭监听器、输入进程和空闲定时器。
- 统一模式不接管旧录像进程；发现同目录仍有活动录像进程时拒绝新增录像，防止重复运行。

## 开发运行

先停止使用同一数据目录的旧服务及其录像进程。开发验证使用独立测试数据目录，
不要同时运行新旧服务连接现场摄像头。

PowerShell：

```powershell
$env:NAVORA_MONITOR_SHARED_INGEST = '1'
npm run build
npm run dev:server
```

切回原链路需停止服务，移除该环境变量后重新启动：

```powershell
Remove-Item Env:NAVORA_MONITOR_SHARED_INGEST
```

这是开发开关，尚未增加界面入口或修改版本号。现场部署前需要完成下面的后续阶段。

## 后续开发与上线门槛

1. **恢复与连续性**：增加统一的重试退避和状态展示。当前沿用原有恢复节奏：预览约 5 秒、
   计划录像约 15 秒、手动录像恢复约 30 秒；断流检测另有最长约 21 秒等待，不能称为无缝恢复。
   测试真实 RTSP 断网、半开连接、重启、参数改变和长时间运行；记录恢复时间及录像缺口。
2. **关键帧启动**：当前缓存按字节窗口保留，不保证包含完整 GOP、PAT/PMT 和编码参数。
   新加入的消费者可能等待后续关键帧；需要实现关键帧感知缓存和长 GOP/H.265 加入测试，
   并验证录像起点、分段时间戳、音视频同步及切段前后无异常缺口。
3. **录像可靠性**：验证慢盘、写满、缓存迁移、循环清理、计划切换和运行中修改设置。
   有界队列溢出会显式断开消费者，可能造成录像缺口，不能宣称在磁盘不足时仍能无损录像。
4. **连接与流量审计**：增加每通道输入连接、接收字节、消费者和断流原因指标。
   真实摄像头验证零观看、单观看、多观看和录像开关组合。手动诊断/探测接口仍可能主动访问源，
   尚未改为复用会话，需审计并明确单独操作的范围。
5. **平台和兼容性**：验证 Windows/Linux、H.264/H.265、不同音频编码、TCP/UDP。
   当前测试源为 HTTP MPEG-TS，不能替代 RTSP 真机验收。统一 MPEG-TS 中间层的编码兼容性
   需要逐项确认，尤其是摄像头的非 AAC 音频。
6. **默认切换**：界面说明统一模式不使用子码流；显示转码负载和明确错误信息。
   满足上述门槛后默认启用，再移除旧双取流实现。

## 验证入口

`go -C server test ./internal/core -run 'TestSharedIngest|TestIngestArgs' -v`
使用本地附带 FFmpeg 和实时 H.264/AAC 测试源，未安装对应平台二进制时跳过集成测试。

- 并发消费者共享同一输入及一次上游请求。
- 部分消费者释放不影响剩余消费者；空闲延迟可取消，最终释放会关闭进程。
- 同时录像和预览仅一次取流，重开预览复用输入，停止录像后预览仍占有输入。
- 录像文件包含并可解码音视频。
- 输入进程失败后重新申请只创建一个替代输入，旧引用释放不影响新会话。

上线验收还需要完整项目回归以及上述真实摄像头测试；自动测试不构成现场连续性保证。
