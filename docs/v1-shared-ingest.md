# v1：统一取流框架与实施进度

## 目标与版本边界

基线为 main 的 `d33dc45`（0.4.4）。v1 在独立分支开发，不修改 main 的运行方式。
优先顺序：录像可靠性、消除摄像头重复取流、预览响应、降低本机开销。

同一通道的录像和实时预览共用一个摄像头输入。多个浏览器共享预览输出。
这里减少的是摄像头到服务端的重复流量；本地分发、服务端到观看者的必要流量依然存在。
原始录像不为浏览器兼容性降质，预览可单独转 H.264。

## 架构决策

第一阶段继续使用外部 FFmpeg，不将原生库嵌入 Go 主服务。
Go 的统一取流管理器按通道维护输入会话；一个 FFmpeg 接收摄像头流，复制原编码
并封装为连续 MPEG-TS。Go 通过仅监听 127.0.0.1 的随机端口和随机路径向本机消费者分发。
录像 FFmpeg 和预览 FFmpeg 各读本地 URL，不再直接读取摄像头。

```text
摄像头 -- 一个输入 --> 取流 FFmpeg --> Go 有界分发
                                      ├─ 录像 FFmpeg：原码流分段写盘
                                      └─ 预览 FFmpeg：直通或按需转码
                                             └─ 现有 HTTP 分发 --> 多个浏览器
```

媒体进程故障与 Go 服务隔离。录像和预览仍是独立消费者，故障或停止不主动停止另一个分支。
DLL 可以作为后续取流后端，但不是消除重复连接的前置条件。

## 第一阶段已实现

- 环境变量 `NAVORA_MONITOR_SHARED_INGEST=1` 在服务启动时启用；默认仍走原有链路。
- 同一通道并发申请只启动一个输入进程；会话匹配主 URL 和 RTSP transport。
- 输入保留视频和可选音频，原编码复制；预览分支继续沿用现有 H.264 转码逻辑。
- 统一模式使用 `URL`，不连接 `PreviewURL`。旧配置不被改写。
- 引用计数控制生命周期；最后一个消费者退出 3 秒后关闭输入，期间新消费者可复用连接。
- 输入地址或 transport 改变时，等待旧输入退出，再建立新输入。
- 输入进程退出或超过 20 秒没有输出时，关闭本地输出，让消费者发现断流。
- 下次消费者申请创建新输入，后续申请共享这个替代会话；重试策略见第二阶段。
- 每个本地消费者最多缓存 128 个输出块，每块约 32 KiB；慢消费者断开，不阻塞其他消费者。
- HTTP 写入设有 3 秒超时；启动缓存已升级为第二阶段的关键帧缓存。
- 服务停止时统一关闭监听器、输入进程和空闲定时器。
- 统一模式不接管旧录像进程；发现同目录仍有活动录像进程时拒绝新增录像，防止重复运行。

## 第二阶段已实现：恢复、关键帧启动和状态

- 统一模式每秒检查当前录像和预览需求，不再等待原来的 15/30 秒录像恢复周期。
- 同一通道共用指数退避：1、2、4、8、16、30 秒，之后上限 30 秒。多个消费者不会各自开启重试输入。
  稳定运行至少 30 秒后再失败会重置退避；改源地址或 transport 也会使用独立的新预算。
- 用户停止录像、移除观看需求后不再恢复。录像恢复与停止操作串行，并在锁内重新确认需求，
  避免旧需求快照把用户刚停止的录像重新拉起。
- 修复 Windows 进程存活检测：可打开进程句柄不等于进程仍在运行。
  现在检查进程是否已终止，且已等待退出的录像会话不会被当作活动录像复用。
- 输入分发与统一模式下的浏览器预览均按完整的 188 字节 TS 包处理；在随机读取边界下也不截断媒体包。
- 新消费者从 PAT/PMT 和最近的随机访问关键帧开始；还没有可用关键帧时等待，不发送前置依赖帧。
  复制视频编码参数到关键帧，并保留探测期间的媒体包，避免探测把启动关键帧丢掉。
  启动会回带最近一个 GOP，因此新开始的录像可能包含点击前的少量画面；精确开始时间和
  浏览器追赶实时位置仍需真机验收。
- 每个启动缓存最多保留 8 MiB 的当前 GOP；超限或丢失包对齐时丢弃启动缓存，等待下一关键帧，
  已接入消费者继续接收流。输入与预览两层缓存各有此上限。
- 运行状态增加 `ingest`：输入状态、消费者引用数、累计中间流字节、输入进程启动次数和下一次重试时间。
  `receivedBytes` 统计 FFmpeg 输出的 TS 字节，不是网卡或 RTSP 协议流量；`starts` 是进程启动次数。
  状态中不包含摄像头地址和本地取流令牌，错误信息去除 URL 账号密码。
- 通道编辑窗口显示统一取流状态，并说明统一模式不使用单独的预览 URL。

关键帧标识来自本程序控制的 FFmpeg TS 输出，固定视频 PID 256、PMT PID 4096；
单节目仅含视频和可选音频，启动缓存只接收完整的单包 PAT/PMT。
实现参考 [FFmpeg MPEG-TS 输出源码](https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/mpegtsenc.c)。

## 开发运行

先停止使用同一数据目录的旧服务及其录像进程。开发验证使用独立测试数据目录，
不要同时运行新旧服务连接现场摄像头。

PowerShell：

```powershell
$env:NAVORA_MONITOR_SHARED_INGEST = '1'
npm run build
npm run dev:server
```

切回原链路需停止服务，移除该环境变量后重新启动：

```powershell
Remove-Item Env:NAVORA_MONITOR_SHARED_INGEST
```

这是开发开关，尚未增加界面入口或修改版本号。现场部署前需要完成下面的后续阶段。

## 后续开发与上线门槛

1. **恢复与连续性**：统一重试退避与状态已完成。当前一秒检查一次需求，并遵守上面的退避时间；
   静默断流检测另有最长约 21 秒等待，不能称为无缝恢复。
   测试真实 RTSP 断网、半开连接、重启、参数改变和长时间运行；记录恢复时间及录像缺口。
2. **关键帧启动**：关键帧缓存与 H.264/H.265 长 GOP 加入测试已完成。
   真实摄像头仍需验证不同 GOP、参数集变化、H.265 随机访问画面及超限等待行为，
   并验证录像起点、分段时间戳、音视频同步及切段前后无异常缺口。
3. **录像可靠性**：验证慢盘、写满、缓存迁移、循环清理、计划切换和运行中修改设置。
   有界队列溢出会显式断开消费者，可能造成录像缺口，不能宣称在磁盘不足时仍能无损录像。
4. **连接与流量审计**：已增加输入状态、TS 输出字节、消费者引用数和重试信息；还需精确网络流量测量。
   真实摄像头验证零观看、单观看、多观看和录像开关组合。手动诊断/探测接口仍可能主动访问源，
   尚未改为复用会话，需审计并明确单独操作的范围。
5. **平台和兼容性**：验证 Windows/Linux、H.264/H.265、不同音频编码、TCP/UDP。
   当前测试源为 HTTP MPEG-TS，不能替代 RTSP 真机验收。统一 MPEG-TS 中间层的编码兼容性
   需要逐项确认，尤其是摄像头的非 AAC 音频。
6. **默认切换**：界面已说明统一模式不使用子码流；还需显示转码负载并完成界面验收。
   满足上述门槛后默认启用，再移除旧双取流实现。

## 验证入口

`go -C server test ./internal/core -run 'TestSharedIngest|TestIngestArgs' -v`
使用本地附带 FFmpeg 和实时 H.264/AAC 测试源，未安装对应平台二进制时跳过集成测试。

- 并发消费者共享同一输入及一次上游请求。
- 部分消费者释放不影响剩余消费者；空闲延迟可取消，最终释放会关闭进程。
- 同时录像和预览仅一次取流，重开预览复用输入，停止录像后预览仍占有输入。
- 录像文件包含并可解码音视频。
- 输入进程失败后重新申请只创建一个替代输入，旧引用释放不影响新会话。
- 当前录像和预览需求在断流后恢复到同一输入；退避期间停止不会被恢复逻辑撤销。
- 静默连接触发超时退出，重试预算递增并封顶，错误状态不泄露 URL 账号密码。
- 持有旧进程句柄时，Windows 仍能正确识别进程已经终止。
- 分片读取、包对齐、启动等待与缓存上限；H.264/H.265 长 GOP 加入前后逐帧解码结果一致。

上线验收还需要完整项目回归以及上述真实摄像头测试；自动测试不构成现场连续性保证。
