## 发现与优化项

### P1 / A1：大时间轴消息会终止 WebSocket 写协程（代码确定，未做端到端故障复现）

证据：`server/internal/core/ws.go` 的 `pushTimeline` 将 segments 与 saved 全量序列化；`writeWSFrame` 对长度 >=65536 的消息直接返回错误；`writeLoop` 遇错直接返回，没有同步关闭连接、通知读循环或注销客户端。历史列表足够大时，时间轴消息必然撞上大小限制，写协程退出，连接可能继续显示为 OPEN。前端有新鲜度和 HTTP 降级逻辑，因此不能直接断言界面必然永久不刷新，但推送失效与退化为额外查询是明确风险。

同一文件 `send` 在队列满时静默丢弃，`pushTimeline` 在实际送达前已记下目录指纹；没有版本确认/重同步协议，不能保证关键更新最终送达。写操作也没有独立截止时间，慢客户端可能卡在持有 cl.mu 的网络写入，影响读取其 watch 状态。

建议：先修复大帧或有界分片，写失败主动关闭连接；限定写超时，分离连接写锁与订阅状态锁；补版本化快照与重同步。验收包含 65535/65536 字节边界、超过 1 MiB 的真实结构列表、慢读客户端、队列溢出、重连恢复，以及健康客户端持续收到状态。

### P1 / A2：服务端历史目录仍被高频全量遍历（代码确定，影响幅度待测）

证据：`record.go` 每 2 秒 pushTimelines、每 5 秒 reconcileMediaMetadata；`ws.go:timelineDirFP` 对被观看通道的目录 ReadDir 并逐文件 Info；`media_index.go:reconcileMediaMetadata` 先 ListRecordings/ListSaved 全量建立候选，再限制最多探测两项。探测预算没有限制前面的目录与索引读取成本。实时录像增长还会持续改变指纹并触发全量列表传输。

建议：先对 1 万/10 万文件目录测接口 p50/p95、扫描耗时、响应大小和磁盘读取量；然后实现按通道和时间范围分页、缓存目录快照、录像关闭/搬运/删除事件更新与低频对账。优先保持现有 JSON 可重建机制，是否引入 SQLite 由实测决定。

### P1 / A3：不同数据目录仍可共用媒体目录（保护范围缺口）

证据：`server/cmd/navora/data_lock.go` 的实例锁位于数据 root；`paths.go` 的录像、缓存、保存目录可独立配置。数据目录锁不能覆盖两个实例配置到同一媒体目录的情况。进程内租约也无法保护另一进程的清理和写入。旧实施记录明确保留了此限制。

建议：对实际可写媒体根目录建立跨进程所有权保护，覆盖启动和运行时存储切换；处理 Windows 大小写、目录别名和路径重叠。验收两个不同 data root 指向同一媒体根时第二实例安全拒绝，切换失败保留原目录与录像状态，异常退出后可恢复。

### P1 / A4：自动校验主要发生在发布阶段

证据：当前 `.github/workflows/release.yml` 仅标签推送和手动触发；执行前端测试和后端检查，但无普通 PR/push 检查。浏览器脚本依赖本机 Windows Edge 路径，不在当前 Linux 发布流程中运行。

建议：增加普通 PR 校验，Windows/Linux Go 测试及静态检查；独立 Windows 媒体/浏览器任务。完整实媒体用例必须明确必需条件与跳过统计，不能缺少 FFmpeg/样本时仍显示媒体验收完成。使用合成或可公开的固定样本，真实私有录像不入库。先整理当前大量修改，按修复主题分批提交，不把整个工作区作为单个发布变更。

### P2 / A5：FFmpeg 输入版本不固定，构建可复现性不足

证据：`scripts/fetch-ffmpeg.mjs` 使用 master-latest 资产与 latest 下载地址，流水线复用缓存。缓存与下载日期不同可能得到不同媒体引擎；项目已有相关参数兼容回归历史。

建议：固定上游构建标识、资产名称与校验摘要；更新引擎时显式更新清单、缓存键和合成媒体回归。不能仅凭归档大小或记录版本文本认定下载内容一致。

### P2 / A6：导出缺少可恢复任务模型

证据：`http.go:handleExportClip` 在请求内等待 ExportRangeContext，结束后返回最终路径；已有取消和调度，不等于任务持久化与恢复。ActivityCenter 作为操作提示也不能替代任务状态存储。

建议：任务 ID、阶段、进度、取消、完成文件入口和有界历史；明确重启后恢复/失败语义及输出文件幂等发布。先保证任务状态真实，再提供重启重试。验收断网、刷新、取消、服务重启、磁盘不足及发布成功但响应丢失。

### P2 / A7：完整兼容与长时间性能验收仍不足

当前有基础合成媒体检查和既有实样本修复记录，但本轮没有全矩阵证据。增加 H.264/HEVC、长 GOP、无声/G.711/AAC、PTS 跳变、截断、跨缺口、倍速以及混合编码导出矩阵。增加 1/8/16 路、跨盘搬运/清理与播放并行、至少 24 小时运行，记录 CPU、内存、进程数、首帧/定位/跨段 p95。

连续播放目前仍为单元素切换，不应直接承诺无缝；先测真实样本，超过门槛再试点短分片连续播放。安装/升级/回滚、LocalService 权限、重启自启需独立现场验收。

### P3 / A8：可维护性与文档收敛

`src/App.vue` 同时承担大量状态与操作，`http.go` 集中路由和多个领域处理。建议在已有回归保护下逐步提取时间轴数据、播放会话、任务与存储状态，不做一次性重写。旧优化计划与实施记录存在历史状态交错，应以本报告为检查快照，后续每项记录“已实现/已自动验证/已现场验收”。README 的版本示例与准备条件也应随发布维护。

HLS 已按需加载，单纯消除构建大包警告不列为高优先级；暂不建议重写播放器、全面换数据库或提升转码并发。

## 下一步执行顺序与验收

1. **阶段一：可靠性修复。** 保存基线；优先 A1，再 A3，补相应边界与并发回归。完成标准：大列表/慢连接不使推送悄然失效；共享媒体目录冲突可安全拒绝。
2. **阶段二：验证与可复现发布。** A4/A5；把本轮已有命令变为 PR 门禁，锁定 FFmpeg，记录实际跳过用例。完成标准：新环境能重建同一引擎版本，Windows/Linux 检查与基础浏览器回归自动执行。
3. **阶段三：服务端规模优化。** 先冻结 A2 的基线，再实现范围查询、增量更新和目录缓存，回归同名冲突、写入中片段、租约、删除与外部导入。完成标准：公布 1 万/10 万文件前后对比，常规刷新不随全部历史文件数线性扫描；候选范围查询 p95 <=200 ms，需在目标硬件上确认后冻结。
4. **阶段四：体验与任务。** A6/A7；优先可观察的导出任务、错误与重试，再根据跨段测量决定连续播放架构。候选热缓存首帧 p95 <=2 秒、定位 p95 <=1 秒、无缺口跨段间隙 p95 <=300 ms；这些是验收目标，本轮未证明达到。
5. **发布前验收。** 完整编码矩阵、24 小时混合负载、低空间/跨盘、安装升级回滚与现场摄像头。任何未测项明确保留，不以单元测试或元数据微基准代替。

不承诺固定工期；A1、A3 为建议的首批独立变更，其余按测量与现场条件安排。优先级表示后续处理顺序，不代表本轮已经发生录像丢失或已发现可利用的安全漏洞。
