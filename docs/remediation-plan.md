# 录像可靠性与回放改造方案

状态：实施中，第一轮实现和验证见 [优化实施记录](./optimization-progress.md)。基线：main / 1107a3f / 0.3.38。日期：2026-10-12。

本文是实施规划，不表示所列修复已完成。保留 Go + Vue + FFmpeg，先在单体服务内划分职责；不以拆微服务作为前提。已有录像保持可读，原始媒体完成后不再被后台原地重写。

## 目标与当前证据

用户反馈拖动慢、连续播放冻结、分段交界停顿均存在。代码审查确认正常回放优先走单文件 TS / mpegts.js；定位重建播放器；跨段在 ended 后才加载下一段；自动修复存在先删原文件后替换的风险。底层 TS 随机访问没有关键帧索引，设置 HTTP Range 不能补足时间到字节的映射。

目前未用真实录像测量延迟或硬件负载，不能将代码超时当作实际卡顿时长。基线检查：前端 113 项测试和类型检查通过；Go TestListFSLeafFiles 依赖未创建的临时文件夹具而失败。现有纯函数测试不覆盖浏览器解码和跨段行为。

## 设计约束

- 原始录像不可变；修复和转封装产生独立的、可验证的派生文件。失败不能删除唯一有效副本。
- 归档文件长度和播放分片长度独立配置。短播放分片要对齐实际关键帧，stream copy 不能凭空生成关键帧；不直接把所有录像分段缩短来掩盖问题。
- 源媒体标识包含通道、文件标识和版本；所有派生文件、索引和任务绑定源版本。大小和高精度 mtime 可作初始版本依据；检测外部替换并失效缓存，不能仅复用当前秒级 mtime 键。
- 定位采用最后一次请求优先，统一取消与过期结果隔离；进度显示使用实际媒体位置。
- 正在回放、导出、搬运或派生处理的文件持有租约，清理不得删除；租约有释放、故障恢复与上限，防止永久占用。
- 媒体时间与墙钟时间明确区分；保留真实缺口与断流，不能靠修改 EndMs 填平。
- 播放兼容性按实际视频与音频编码检测。转封装不改变编码，不能把 H.265 包成 MP4 就认定浏览器支持。

## 阶段 0：建立可比较的播放基线

范围：PlaybackView、PlaybackController、StreamEngine、Go 媒体任务及 HTTP 文件服务。先记录而不改变默认播放路径。

记录每次 load/seek 的操作 ID、片段 ID、目标与实际位置、选用引擎、开始/首帧/失败时间、取消原因、缓冲范围、解码与丢帧、恢复原因及次数；服务端记录任务排队/执行耗时、输出大小、缓存命中与取消。日志不得记录 RTSP 密码、认证令牌、完整敏感 URL。浏览器不支持某项指标时明确标为不可用，不能伪造为 0。

建立可复用录像样本：H.264/H.265、有声/无声、不兼容音频、长 GOP、正常分段、断流重连、时间戳跳变、截断文件。先生成可公开的合成夹具；真实问题片段只在本机使用。确认实际摄像头数、常用码率、浏览器、硬盘与缓存是否跨卷。

验收：同一操作可串联前后端记录；能区分网络等待、派生准备、解码未出帧和恢复重载。修正 Go 测试为 t.TempDir 自建夹具。测试基线全部通过后进入后续默认路径变更。

## 阶段 1：先消除录像与导出风险

涉及：media.go、record.go、policy.go、shutdown.go；新增媒体文件租约和派生结果发布模块。

1. 停止自动原地 normalizeTS。自动流程改为必要性检测与生成播放派生副本；手动时间戳修复也保留原文件。原路径若有旧 API 依赖，返回新的可播放引用，不能偷偷覆盖来源。
2. 派生文件在目标目录中创建唯一临时文件，FFmpeg 成功后探测有效视频流、可读性和时长，再发布不可变结果。检查进程退出、磁盘写入和发布错误；失败保留源文件，可恢复临时结果，记录明确原因。不能只用“文件大于 64 字节”判定可用。
3. ExportRange 每任务使用独立临时清单与输出。目标存在时默认生成唯一名称，用户明确指定覆盖时才执行明确的替换策略。获取所有源租约后执行，校验版本，任务结束释放。导出覆盖的时间范围含缺口时明确约定结果时长与时间映射。
4. 媒体任务改用可取消的上下文；取消时终止关联 FFmpeg 进程树并回收租约、临时文件和任务占位。退出时停止接收任务，取消/排空有界工作，避免任务在服务退出后继续发布结果。
5. 清理先选择候选，再在删除前检查活动写入状态及租约；获取租约与删除使用共同的同步边界，避免“检查后又有人开始读取”的竞态。

验收：模拟输出无效、发布失败、磁盘满、进程取消、服务重启；源文件哈希不变且可读取。两个同通道导出互不覆盖。回放/导出与清理并发时源文件不会在使用中被删除，释放后才可回收。Windows 下覆盖、句柄占用和跨卷搬运分别验证。

回退：可以关闭派生生成或恢复旧播放入口；不得恢复先删除原文件的危险替换逻辑。历史 .normed 标志仅兼容读取，不能直接当作媒体有效性证据。

## 阶段 2：修复时间数据与文件生命周期

涉及：media.go 的 segmentBounds/trimSegmentEnds、record.go、shared/types.ts、shared/segment-writing.ts、wall-time.ts、TimelinePanel。

建立最小媒体目录接口：按通道/时间范围列出、分段完成登记、源版本更新、派生状态查询。先做单写者与每通道内存缓存；现有 index.json 暂作兼容持久化，由唯一写入路径更新，临时文件唯一，错误可观测。HTTP/WS 查询不再隐式改写索引。

片段模型至少包含：sourceVersion、recordingState（writing/finalizing/ready/invalid/missing）、wallStart、首尾媒体时间戳、duration、codec、音频信息、时间估计可信度和派生版本。完成状态由录制进程分段事件/关闭后的稳定性校验确认；外部接管和重启后做一次对账。mtime 只作为辅助，不能单独证明关闭。

新录像分段完成后探测实际媒体数据；旧录像懒探测并有界后台补齐，避免启动全盘扫描。探测失败的片段保留在目录中并标注不可用/待检查，不悄悄消失。修正全局与通道分段长度的混用；DefaultSegmentTimeSec 对新建/缺省通道生效，已有显式配置保持不变。

取消 trimSegmentEnds 对真实缺口的填平。时间轴绘制可以合并相邻视觉块，但查找和导出必须使用真实范围。录制重连、摄像头 PTS 重置、时区/夏令时、文件复制导致 mtime 改变都纳入映射规则。派生处理不得分别强制音视频归零而破坏原本同步关系，需记录共同偏移和转换后的起点。

验收：存在 30/90 秒缺口时不显示成可播放内容；拖到缺口按明确策略跳至下一可用段并提示实际落点。新旧录像的实际 duration 与索引一致到合理媒体精度。正在写入的录像不会被预处理或清理，finalizing 可显示准备状态。长分段不会因固定 20 分钟启发式被误判。

回退：保留原 JSON 和源媒体，索引结构带版本；新字段对旧客户端可忽略。旧估计值只能作为低可信度降级，不再填造缺口。

## 阶段 3：单通道试点可靠随机回放

涉及：EnsurePlayable、handlePrepare、媒体路由、PlaybackController、StreamEngine、PlaybackView。

默认仍保留原路径，增加可切换的 native MP4 播放模式，先比较真实样本后再决定是否启用默认。将已完成 TS/MKV 转封装为可随机访问的 faststart MP4；原 MP4 校验后可直接服务。浏览器直接使用 HTTP URL + Range，不能 fetch 整段 blob 后才开始播放。

冷缓存不能伪装成“立即可播放”：准备 API 返回 ready/pending/failed 和任务 ID；前端显示准备与取消，可通过任务状态通知获取结果。同源版本的并发准备合并，已完成缓存直接命中。新录像完成后只预热最近且可能被播放的片段，避免转封装全部历史录像。旧缓存 2 GiB 固定上限改为按卷预算与 LRU，淘汰须避让租约和生成中的任务。

定位：同文件复用 video，已缓冲定位直接 currentTime；跨文件准备完毕后加载新来源。统一 operation generation；新操作立即取消旧 UI 等待与旧 HTTP 订阅，所有回调在更新状态前检查 generation。共享任务还有其它订阅者时不能被单个取消误杀；无人需要时才取消低优先级准备。避免串行等完旧 scrub 的多个超时。

编码策略：支持的 H.264/H.265 与音频优先 copy；不兼容音频按配置生成 AAC 副本，不静默丢音轨。不支持的视频编码先明确提示，按配置允许生成 H.264 播放副本并设资源预算；不默认对所有录像转码。无声视频不强制声明有音轨。损坏片段与不支持编码分别报错。

验收：对同一片段连续随机定位 100 次，最后目标优先，无过期回调覆盖；明确区分冷/热缓存结果。暂停、继续、倍速、音量、截图、全屏和切通道行为通过。H.264/H.265/无声/异常样本得到正确播放或明确兼容性结果；测量首帧与定位延迟，不能只看 play() resolve。

候选性能门槛（待阶段 0 在实际设备确认后冻结）：本机正常 H.264、热缓存、1× 播放，首帧 p95 ≤2 秒，定位 p95 ≤1 秒；随机定位误差 ≤1 秒（精度不足时记录实际落点与 GOP 原因）；连续播放 30 分钟无超过 1 秒的意外冻结。冷缓存准备时长单独报告，不混入热缓存成绩，也不承诺上述数字已达到。

回退：按通道切回旧读取路径，保留新目录和安全修复；记录旧引擎降级原因。只有新路径验证完成后才移除冗余 HLS/TS 恢复分支。

## 阶段 4：后台调度、增量查询与容量保护

涉及：RunLoops、ws.go、media.go、record.go、paths.go、App.vue 与 API bridge。

从一个串行循环拆出健康/计划调度、索引事件处理、搬运/清理和派生任务。进程控制集中管理；同通道开始/停止防重复。媒体任务队列有界，任务去重，前台播放准备优先于历史修复；保留后台最低进度，避免长期饥饿。并发数由实测磁盘/CPU 预算决定，不简单把容量 1 改成无限并发。

目录查询按通道和时间范围分页；WS 首次发快照，后续发版本化增量，重连或版本缺失请求重同步。前端 fallback 轮询防重入、丢弃旧通道结果，避免查询竞争覆盖当前页面。目录指纹不再每秒对所有历史文件 stat；关闭事件负责主更新，低频对账处理外部文件变更。

清理一次读取 stat 信息再排序，避免 O(n²) 与比较中重复 IO；分批删除，及时让出执行权。记录写入累计字节，以滑动窗口增量计算速率；分别统计缓存、归档、派生缓存、保存片段所在卷，共享卷去重。缓存盘满优先停用缓存或有序停止录制，策略必须显式，不能无提示丢片段。

通过媒体目录接口隔离持久化实现。单写者 JSON/内存方案先达标；当跨通道查询和历史规模仍超标时再引入 SQLite，使用版本迁移与可重建目录，不让数据库成为原始录像唯一可恢复入口。

验收：用 1/8/16 通道规模与 1 万/10 万条元数据分别测试查询和清理（元数据测试不能冒充真实多路视频压测）；后台导出/预处理/搬运/清理时计划与健康检查不被长任务阻塞；资源占用有上限。跨卷低空间、源消失、索引损坏、重启对账通过；预测速率与实测写入增量一致。

## 阶段 5：连续跨段播放

阶段 3 的 native MP4 改善单文件定位，但不能保证跨文件无缝。短期在接近段尾时准备下一段并预取必要数据；定义取消、租约和释放时机，验收实际音画间隙，避免并行解码多段导致资源翻倍。若仍有明显切源停顿，则采用下面的连续分片方案。

将归档 TS/MP4 转成按关键帧对齐的短播放分片，起步目标 2–6 秒，实际边界由 GOP 决定；配合 init segment、真实 duration、discontinuity 和墙钟映射构建窗口清单。对长 GOP 明确实际 seek 精度；只有用户配置允许时才用受控转码缩短 GOP。优先按需生成并预热相邻窗口，防止双份历史媒体挤满磁盘。

先在已完成录像上实现；正在录制内容的追播是独立能力，需要 writer 完成事件和只发布已关闭分片，不能把正在增长的 300 秒 TS 直接当成完整 VOD 分片。旧录像继续按需派生，用户无需手动迁移。

HLS.js 与原生 HLS 能力、HEVC、切片封装、音视频时间戳需用样本验证后选择；不能直接启用现有“整段 TS 当一个 HLS fragment”的旧方案。连续播放引擎通过媒体适配层接入，控制器只维护操作与墙钟意图，移除重复恢复逻辑应在等价测试之后。

验收：至少连续跨越 20 个片段，包含真实空档、重连、编码变化和倍速；连续无缺口样本的跨段音画间隙候选 p95 ≤300 ms，真实缺口必须可见且不计为播放器故障。连续运行、内存稳定、缓存淘汰和任务取消通过后，才作为默认连续播放路径。

## 远程访问修复（与阶段 1–3 独立交付）

默认 RemoteEnabled=false 时仅回环监听；启用后按配置绑定局域网。--addr 显式指定与持久设置的优先级写入文档和 UI，不出现关闭开关却仍暴露远程的状态。运行时更改监听要么安全重绑定，要么明确提示需重启，不能假装立即生效。Windows 服务启动路径与控制台采用同一策略。

密码变更撤销已有会话，也断开持有旧会话的 WS/SSE/媒体长连接；只清空 sessions 不足以撤销已经鉴权建立的连接。登录增加有界速率限制，不造成永久锁死；本机代理来源不能盲信任 X-Forwarded-For。维持 cookie HttpOnly/SameSite；启用 HTTPS 时加 Secure。部署到不可信网络时采用 TLS 终止与访问控制，不把随机密码当作传输加密。

验收：默认远程连接不可达，本机仍可用；启用后可达；改密码后旧 API、媒体和现有长连接均失效。服务模式、端口占用、重启、错误配置有明确状态。

## 建议提交拆分与依赖

每项是独立可审查的提交或 PR，按完成内容命名，不预先创建空 PR。

1. 测试自包含性与播放指标：阶段 0。
2. 源录像保护与安全派生发布：阶段 1 的修复流程。
3. 导出隔离、文件租约与清理协调：依赖 2。
4. 远程开关、改密撤销和登录限制：可独立推进。
5. 媒体生命周期、真实时间数据与 JSON 单写者：依赖 2、3。
6. 有界可取消任务、独立后台调度：依赖 2、3；为预热和准备 API 提供基础。
7. MP4 播放准备与缓存、编码兼容：依赖 5、6。
8. 前端定位取消、native 播放试点与浏览器回归：依赖 1、7。
9. 增量查询/WS、清理性能和多卷容量：依赖 5、6。
10. 下一段预取与跨段测试：依赖 8、9。
11. 按需短分片连续播放与旧路径收敛：依赖 10 的实测结果；MP4 试点若不能覆盖主要编码，则提前评估分片路线。

执行顺序先安全、再单通道回放、再多通道扩展。当前缺少样本和性能基线，不给固定工期；阶段 0 完成后按媒体兼容性与存储规模估算。

## 发布与回退

安全修复先发布；新播放模式先单通道启用，再扩大默认范围。记录配置/索引版本并备份配置，派生文件可删除重建，不能依赖回退才能恢复源录像。迁移不会批量重写历史录像。每次发布保留旧录像读取兼容性、明确回退开关和失败状态。

每个阶段运行相关 Go/前端检查；媒体安全与并发变更增加故障/竞态测试，播放器变更增加真实浏览器测试。最终至少进行 24 小时录制与混合回放稳定性观察；多日保留和低空间回收用可控时钟与空间模拟另验，不能用 24 小时观察替代所有保留策略验证。
